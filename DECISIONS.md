## Domain & Scope
- Decision: Distributor-Agreement-only, CUAD-sourced, presence + deviation-detection (no severity scoring). Pivoted from the originally-planned NDA domain in Phase 0.
- Reasoning: [in your own words — bounded ground truth, no legal background to defend risk judgments]
- Pivot detail: CUAD's 510 contracts are organized into 25 documented business-relationship types (Distributor, License, Franchise, Consulting, Joint Venture, Supply, etc.) — NDA is not one of them. Verified directly, not assumed: searched all 510 titles + lawyer-labeled "Document Name" answers for NDA/confidentiality keywords, found 2 loose hits, neither an actual NDA. Considered building NDAs from an unlabeled source instead (e.g. scraping SEC EDGAR the way CUAD's own scrape.py does) but rejected — that would mean hand-building the entire ground truth with no lawyer labels to derive it from, which breaks the 1-week timeline and the whole point of using an expert-annotated dataset. Picked Distributor Agreement over the runner-up, License Agreement, using measured clause coverage, not doc count alone: License has more docs (36 vs 31) but Distributor wins on 4 of the 5 checklist categories that appear in both — Non-Compete (42% vs 20%), Termination-for-Convenience (42% vs 34%), Cap-on-Liability (68% vs 59%), Anti-Assignment (81% vs 76%); License only wins on IP Ownership Assignment (29% vs 10%), which was dropped from the checklist anyway (see below).
- Rejected: general multi-tool agent (no coherent ground truth possible across unrelated tasks); data-cleaning automation agent (heavier ground-truth burden than a decision-memo project, and drops the "document" framing entirely); weighted/graded legal-risk scoring (needs legal expertise not held).

## Corpus Cleaning
- Decision: excluded 4 of the 31 CUAD Distributor Agreement entries — all are amendment/addendum riders to an already-executed agreement, not standalone contracts: `NETGEAR,INC...AMENDMENT TO THE DISTRIBUTOR AGREEMENT...`, `NEONSYSTEMSINC...DISTRIBUTOR AGREEMENT_Amendment`, `ScansourceInc_20190509...` (opens "ADDENDUM TO ZEBRA PARTNERCONNECT DISTRIBUTOR AGREEMENT"), `ScansourceInc_20190822...EX-10.39` (opens "AMENDMENT NO. 3 TO THE NONEXCLUSIVE VALUE ADDED DISTRIBUTOR AGREEMENT"). Working corpus is **27 documents**.
- Reasoning: an amendment/addendum document typically only contains the specific clause(s) being modified. Grading it against the full 8-category checklist would record most categories as "absent" not because the underlying deal actually lacks them, but because the rider PDF never restates them — a labeling artifact, not a real signal.
- Caught in two passes, not one: the first pass (2 exclusions) only checked CUAD's *title* metadata for the word "amendment" — this missed 2 more riders whose CUAD title looks like a normal full agreement (e.g. `..._Distributor Agreement`) but whose actual body text opens with "AMENDMENT NO. 3 TO..." or "ADDENDUM TO...". Found when a spot-check reader (not me) got confused by the first-pass "0/8 clauses, easiest to start with" example — it turned out to *be* one of the missed amendments, not a genuinely clause-empty full agreement. Fixed by scanning every doc's opening ~1200 characters for AMENDMENT/ADDENDUM/AMENDED-AND-RESTATED language instead of trusting the title field alone.
- Impact: dev set stays 20 docs; full-validation set shrinks from 9 to 7 (27 − 20). Checklist coverage percentages recomputed on the clean 27-doc corpus are all *higher* than the earlier (29-doc, still-dirty) numbers — consistent with the removed docs being non-representative outliers, not a sign the checklist choice was wrong.
- What I'd change if I did it again: scan document body text for structural/rider indicators (amendment, addendum, exhibit-within-exhibit) as a standard first step of corpus loading, not an afterthought triggered by a confusing example downstream.

## Checklist Categories
- Decision: 8 categories — Governing Law, Non-Compete, Termination for Convenience, Cap on Liability, Uncapped Liability, Anti-Assignment, Exclusivity, License Grant.
- Reasoning: measured presence rate across the clean 27-doc CUAD Distributor Agreement corpus (4 amendment/addendum riders excluded — see "Corpus Cleaning" above) for every one of CUAD's 41 clause categories (not guessed). Kept the 6 categories from the original NDA-oriented checklist that still had reasonable coverage in this domain (Governing Law 100%, Non-Compete 48%, Termination-for-Convenience 48%, Cap-on-Liability 78%, Uncapped-Liability 26%, Anti-Assignment 89%). Dropped No-Solicit-of-Employees and IP Ownership Assignment — both near-absent (~5-10% on the pre-cleaning corpus), expected since neither is core to a distributor relationship. Replaced with Exclusivity (70%) and License Grant (85%) — both central to what a distributor agreement actually negotiates (exclusive vs. non-exclusive territory, what's being licensed to distribute). Uncapped Liability is kept despite thin coverage (26%) deliberately — it's a paired red-flag category with Cap on Liability (absence-of-a-cap is the interesting/rare finding, not something to optimize away for a higher coverage number).
- Rejected: keeping the original NDA-oriented 8 unchanged (would ship 2 checklist items that almost never fire in this domain, weakening the whole "X of Y clauses present" signal); swapping Uncapped Liability for a higher-coverage category — considered, but would lose the deliberate Cap/Uncapped-Liability paired-flag design carried over from the original plan.

Worktrees are **never deleted** after merging — kept around until the whole project is complete, only removed then if needed. (Phase 0's worktree was deleted right after merge on the first pass, per an earlier draft of this rule; corrected and the worktree recreated at the user's instruction.)

Forcing OpenCode to explain its reasoning turns its output into something Claude can actually audit, instead of a black box to trust or not.

## Ground Truth — Spot-Check Result
- Decision: spot-checked 4 dev-set docs (`SmartRxSystemsInc..._Distributor Agreement` 3/8, `LIMEENERGYCO...` 4/8, `ETELOS,INC...` 6/8, `ZogenixInc...` 8/8 — spans the corpus's clause-richness range). Remaining 16 dev-set docs and all 7 full-validation docs are trusted as-is from CUAD's published, lawyer-verified labels, not individually re-verified.
- Method: (1) every PRESENT label's quote checked against a plain-English definition of the category — does the excerpt actually contain the category's telltale language; (2) every ABSENT label swept with a category-specific keyword search (`scripts/self_check_absent.py`) across the full contract text, and every hit manually read in full surrounding context.
- Result: zero discrepancies. All flagged keyword hits were false alarms — a heading mentioning "LIMITATION OF LIABILITY" over a section that was actually just warranty disclaimers (with the real liability-cap subsection literally marked "INTENTIONALLY LEFT BLANK" in the source); two "either party may terminate ... upon written notice" clauses that turned out to require a specific triggering condition (breach, insolvency, bankruptcy) — i.e. termination for cause, not for convenience; and six "exclusive" keyword hits that were all actually "**non**-exclusive," the opposite of what the category checks for.
- Reasoning: this spot-check is verifying the extraction/formatting pipeline (my code correctly wiring CUAD's spans to the right doc/category), not re-litigating CUAD's own lawyer annotation — that's the trust boundary this project relies on (cite CUAD's own published inter-annotator-agreement stats as the justification for not re-verifying every row of a 41-category, 510-document expert-labeled benchmark by hand). A zero-discrepancy result across a richness-representative sample is evidence the pipeline is wired correctly, not proof CUAD is right about every one of the ~1600 individual clause calls in the full corpus.

## PDF Sourcing
- Decision: sourced the actual PDF files from the official full CUAD_v1 release on Zenodo (DOI 10.5281/zenodo.4595826, CC-BY-4.0, 105MB, checksum-verified) rather than only the lightweight text-only JSON from the GitHub code repo used earlier.
- Reasoning: the GitHub repo's `data.zip` (used in Phase 0 so far) only ships CUADv1.json -- lawyer labels + pre-extracted text, no actual PDF files. The pipeline's Step 1 (pdfplumber PDF extraction) needs real PDFs to test against; text-only JSON can't exercise that step at all.
- Verification bonus: the full Zenodo release organizes contracts into CUAD's own official type folders (`full_contract_pdf/Part_I|II|III/Distributor/...`). Cross-checked all 31 title-matched docs against this official folder structure -- all 31 are independently confirmed as CUAD's own "Distributor" type (just split across three Part_ folders, not one), corroborating the domain-pivot and corpus-selection decisions above from a second, independent source rather than just the title-substring heuristic.
- Impact: 27 clean-corpus PDFs copied to `data/pdfs/` with a `manifest.json` mapping CUAD title -> PDF filename, for Phase 1 to consume directly.
