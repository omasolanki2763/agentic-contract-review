## Domain & Scope
- Decision: Distributor-Agreement-only, CUAD-sourced, presence + deviation-detection (no severity scoring). Pivoted from the originally-planned NDA domain in Phase 0.
- Reasoning: [in your own words — bounded ground truth, no legal background to defend risk judgments]
- Pivot detail: CUAD's 510 contracts are organized into 25 documented business-relationship types (Distributor, License, Franchise, Consulting, Joint Venture, Supply, etc.) — NDA is not one of them. Verified directly, not assumed: searched all 510 titles + lawyer-labeled "Document Name" answers for NDA/confidentiality keywords, found 2 loose hits, neither an actual NDA. Considered building NDAs from an unlabeled source instead (e.g. scraping SEC EDGAR the way CUAD's own scrape.py does) but rejected — that would mean hand-building the entire ground truth with no lawyer labels to derive it from, which breaks the 1-week timeline and the whole point of using an expert-annotated dataset. Picked Distributor Agreement over the runner-up, License Agreement, using measured clause coverage, not doc count alone: License has more docs (36 vs 31) but Distributor wins on 4 of the 5 checklist categories that appear in both — Non-Compete (42% vs 20%), Termination-for-Convenience (42% vs 34%), Cap-on-Liability (68% vs 59%), Anti-Assignment (81% vs 76%); License only wins on IP Ownership Assignment (29% vs 10%), which was dropped from the checklist anyway (see below).
- Rejected: general multi-tool agent (no coherent ground truth possible across unrelated tasks); data-cleaning automation agent (heavier ground-truth burden than a decision-memo project, and drops the "document" framing entirely); weighted/graded legal-risk scoring (needs legal expertise not held).

## Corpus Cleaning
- Decision: excluded 4 of the 31 CUAD Distributor Agreement entries — all are amendment/addendum riders to an already-executed agreement, not standalone contracts: `NETGEAR,INC...AMENDMENT TO THE DISTRIBUTOR AGREEMENT...`, `NEONSYSTEMSINC...DISTRIBUTOR AGREEMENT_Amendment`, `ScansourceInc_20190509...` (opens "ADDENDUM TO ZEBRA PARTNERCONNECT DISTRIBUTOR AGREEMENT"), `ScansourceInc_20190822...EX-10.39` (opens "AMENDMENT NO. 3 TO THE NONEXCLUSIVE VALUE ADDED DISTRIBUTOR AGREEMENT"). Working corpus is **27 documents**.
- Reasoning: an amendment/addendum document typically only contains the specific clause(s) being modified. Grading it against the full 8-category checklist would record most categories as "absent" not because the underlying deal actually lacks them, but because the rider PDF never restates them — a labeling artifact, not a real signal.
- Caught in two passes, not one: the first pass (2 exclusions) only checked CUAD's *title* metadata for the word "amendment" — this missed 2 more riders whose CUAD title looks like a normal full agreement (e.g. `..._Distributor Agreement`) but whose actual body text opens with "AMENDMENT NO. 3 TO..." or "ADDENDUM TO...". Found when a spot-check reader (not me) got confused by the first-pass "0/8 clauses, easiest to start with" example — it turned out to *be* one of the missed amendments, not a genuinely clause-empty full agreement. Fixed by scanning every doc's opening ~1200 characters for AMENDMENT/ADDENDUM/AMENDED-AND-RESTATED language instead of trusting the title field alone.
- Impact: dev set stays 20 docs; full-validation set shrinks from 9 to 7 (27 − 20). Checklist coverage percentages recomputed on the clean 27-doc corpus are all *higher* than the earlier (29-doc, still-dirty) numbers — consistent with the removed docs being non-representative outliers, not a sign the checklist choice was wrong.
- What I'd change if I did it again: scan document body text for structural/rider indicators (amendment, addendum, exhibit-within-exhibit) as a standard first step of corpus loading, not an afterthought triggered by a confusing example downstream.

## Checklist Categories
- Decision: 8 categories — Governing Law, Non-Compete, Termination for Convenience, Cap on Liability, Uncapped Liability, Anti-Assignment, Exclusivity, License Grant.
- Reasoning: measured presence rate across the clean 27-doc CUAD Distributor Agreement corpus (4 amendment/addendum riders excluded — see "Corpus Cleaning" above) for every one of CUAD's 41 clause categories (not guessed). Kept the 6 categories from the original NDA-oriented checklist that still had reasonable coverage in this domain (Governing Law 100%, Non-Compete 48%, Termination-for-Convenience 48%, Cap-on-Liability 78%, Uncapped-Liability 26%, Anti-Assignment 89%). Dropped No-Solicit-of-Employees and IP Ownership Assignment — both near-absent (~5-10% on the pre-cleaning corpus), expected since neither is core to a distributor relationship. Replaced with Exclusivity (70%) and License Grant (85%) — both central to what a distributor agreement actually negotiates (exclusive vs. non-exclusive territory, what's being licensed to distribute). Uncapped Liability is kept despite thin coverage (26%) deliberately — it's a paired red-flag category with Cap on Liability (absence-of-a-cap is the interesting/rare finding, not something to optimize away for a higher coverage number).
- Rejected: keeping the original NDA-oriented 8 unchanged (would ship 2 checklist items that almost never fire in this domain, weakening the whole "X of Y clauses present" signal); swapping Uncapped Liability for a higher-coverage category — considered, but would lose the deliberate Cap/Uncapped-Liability paired-flag design carried over from the original plan.

- Reasoning: [why per-minute rate limits and daily quota exhaustion need different handling; why grounding failures skip straight to fallback]

## Timeout
- Decision: 62 seconds per API call (any provider).
- Reasoning: measured real Gemini call latency on 3 sample docs (17.9s, 23.9s, 20.6s; avg 20.8s), then applied the plan's stated rule (3x measured average) rather than guessing a round number. Implemented as a hard thread-based timeout wrapper around every generate call (`retry_policy._call_with_timeout`) -- a timeout is classified as TRANSIENT and enters the same retry-with-backoff path as a network error, since a hung call and a network hiccup need the same response (retry, then escalate).
- What I'd change if I did it again: re-measure once Groq's typical latency is known too (currently only measured against Gemini) -- if Groq's calls run meaningfully faster or slower, a single shared timeout may be too loose for one provider and too tight for the other.

## Ground Truth — Spot-Check Result
- Decision: spot-checked 4 dev-set docs (`SmartRxSystemsInc..._Distributor Agreement` 3/8, `LIMEENERGYCO...` 4/8, `ETELOS,INC...` 6/8, `ZogenixInc...` 8/8 — spans the corpus's clause-richness range). Remaining 16 dev-set docs and all 7 full-validation docs are trusted as-is from CUAD's published, lawyer-verified labels, not individually re-verified.
- Method: (1) every PRESENT label's quote checked against a plain-English definition of the category — does the excerpt actually contain the category's telltale language; (2) every ABSENT label swept with a category-specific keyword search (`scripts/self_check_absent.py`) across the full contract text, and every hit manually read in full surrounding context.
- Result: zero discrepancies. All flagged keyword hits were false alarms — a heading mentioning "LIMITATION OF LIABILITY" over a section that was actually just warranty disclaimers (with the real liability-cap subsection literally marked "INTENTIONALLY LEFT BLANK" in the source); two "either party may terminate ... upon written notice" clauses that turned out to require a specific triggering condition (breach, insolvency, bankruptcy) — i.e. termination for cause, not for convenience; and six "exclusive" keyword hits that were all actually "**non**-exclusive," the opposite of what the category checks for.
- Reasoning: this spot-check is verifying the extraction/formatting pipeline (my code correctly wiring CUAD's spans to the right doc/category), not re-litigating CUAD's own lawyer annotation — that's the trust boundary this project relies on (cite CUAD's own published inter-annotator-agreement stats as the justification for not re-verifying every row of a 41-category, 510-document expert-labeled benchmark by hand). A zero-discrepancy result across a richness-representative sample is evidence the pipeline is wired correctly, not proof CUAD is right about every one of the ~1600 individual clause calls in the full corpus.

## Phase 1 — Happy-Path Validation
- Decision: proved the pipeline shape on 3 sample docs (SmartRx 3/8 richness, Etelos 6/8, Zogenix 8/8 — same docs already spot-checked in Phase 0, so results are directly comparable to hand-verified ground truth).
- Result: 23/24 clause-level calls correct (95.8%) on this tiny sample. Etelos and Zogenix: exact match, 8/8 and 6/8 respectively. The model conflated "warranty disclaimer" with "liability cap." No hallucinated/ungrounded quotes on any of the 3 docs -- the grounding check never had to reject anything.
- Reasoning: 3 docs is nowhere near enough to claim an accuracy number (that's Phase 4's job, over the full 20-doc dev set) -- this only proves the pipeline's shape works end to end and gives one concrete, already-understood failure mode to watch for when prompt-tuning later.
- What I'd change if I did it again: nothing yet -- too early, this is exactly the kind of miss Phase 4's regression suite and prompt iteration is supposed to catch and fix.

## Phase 2 — Fault Injection Testing
- Decision: tested every failure path in the chain, not just the happy path -- two real (unmocked) induced failures plus 5 mocked unit tests for the failure types that don't reproduce reliably on demand from a live API.
- Real tests: (1) invalid Gemini API key + real Groq key -> pipeline correctly escalated to the Groq tier, produced a correct memo (6/8, matches ground truth), flagged `fallback_used: true` / `fallback_tier: groq`. (2) invalid keys on *both* Gemini and Groq -> escalated all the way to the rule-based tier, still produced a correct memo (6/8), never crashed, never returned nothing.
- Mocked tests (`tests/test_retry_policy.py`): TRANSIENT retries exactly 2x with real exponential backoff (timed: >=6s elapsed for 2s+4s) then fails the tier; MALFORMED_OUTPUT retries exactly 1x with a corrective instruction actually appended to the second call; GROUNDING_FAILURE and QUOTA_EXHAUSTED both fail on the first attempt with zero retries, per the plan's reasoning that retrying either just reproduces the same failure.
- Reasoning: this is the literal Phase 1 deliverable text ("pipeline survives induced failures ... without ever crashing or returning nothing") -- verifying it by actually breaking things, not by reading the retry code and assuming it works.

## Phase 2 — Independent Code Review (Opus)
- Decision: before merging, ran an independent review (Claude Opus, fresh context, no prior conversation state) against every Phase 2 source file plus the actual installed SDK versions in `.venv` (google-genai 2.19.0, groq 1.6.0), specifically targeting whether the "never crash, never return nothing" guarantee actually holds -- not a style pass.
- Reasoning: the fault-injection testing above (real bad-key tests, mocked unit tests) proves the *retry/escalation logic* handles the 4 documented failure types correctly. It does not prove the code around that logic is crash-proof against LLM output that's malformed in ways those tests didn't construct, or against infrastructure failures (missing key, unreadable PDF, resource exhaustion) outside the retry loop's scope. An independent model with no stake in the code already "working" is better positioned to find exactly that gap than re-reading my own code looking for confirmation it's fine.
- Findings and fixes (all applied, same commit):
  - **Crash risk in the parse/ground stage** (`retry_policy.py`): only `ValueError`/`KeyError` were caught after `parse_fn`, and `ground_fn` wasn't wrapped at all. LLM output that's valid JSON but the wrong *shape* (array instead of object, quote objects instead of strings, a bare bool) raised `AttributeError`/`TypeError` that escaped the whole fallback chain instead of being classified `MALFORMED_OUTPUT` and retried. Fixed: `parse_fn`+`ground_fn` now share one `except Exception` that classifies as `MALFORMED_OUTPUT`; `clause_extraction.ground_quotes` now raises `ValueError` on any shape it doesn't recognize instead of assuming it.
  - **Unchecked empty/None provider response** (`gemini_provider.py`, `groq_provider.py`): `response.text` (Gemini) and `response.choices[0].message.content` (Groq) are both nullable in the installed SDKs -- a safety block, `MAX_TOKENS` with only thinking-tokens, or an empty choices list all feed straight into the crash above. Fixed: both now raise `ValueError` on empty/missing text, which the retry policy classifies `MALFORMED_OUTPUT` and gives the documented one corrective retry.
  - **PDF extraction had no failure handling at all** (`fallback_pipeline.py`): a missing/corrupt PDF crashed before any tier ran; a scanned/image-only PDF silently returned `""` and the chain reported a confident "0 of 8 present" with no signal the document was never actually read. Fixed: extraction wrapped in `try/except`, plus a `MIN_EXTRACTED_CHARS = 500` floor -- either produces a distinct `extraction_failed` memo instead of a misleading all-tiers-agree-on-nothing result.
  - **Missing (not just invalid) API key crashed before the chain started** (`run_pipeline.py`): `genai.Client()`/`groq.Groq()` raise immediately on a missing key, which the earlier fault-injection tests never exercised (those used *invalid* keys, which reach the tier and escalate correctly). Fixed: client construction is now guarded, returns `None` on failure, and `_run_llm_chain` skips a `None` tier and records it in `tier_attempts` rather than crashing or silently omitting it.
  - **The fallback-warning line crashed the CLI, only on the fallback path** (`memo.py`): the `⚠` character isn't encodable on this machine's Windows cp1252 stdout -- so the pipeline survived every induced API failure and then died printing the warning about it. Fixed: ASCII-only warning text.
  - **`ThreadPoolExecutor`-based timeout leaked non-daemon worker threads** (`retry_policy._call_with_timeout`): a genuinely hung call (no native SDK timeout was set) left its worker thread running after the wrapper gave up on it; `concurrent.futures`' atexit handler joins all such threads before the process can exit, so a single stuck call could hang the whole process at shutdown, and a shared module-level pool could starve after a few leaked calls, silently misreporting later calls as provider failures when the provider was never even contacted. Fixed: replaced with a daemon `threading.Thread` per call (abandoned cleanly on timeout, can't block exit or starve a pool) and added real provider-level timeouts (`genai.Client(http_options=HttpOptions(timeout=...))`, `groq.Groq(timeout=...)`, both set a few seconds under `CALL_TIMEOUT_SECONDS`) as the first line of defense, with the thread-join as backstop.
  - **5xx server errors weren't classified TRANSIENT** (`failure_types.py`): only `"unavailable"` was covered; a 500/502/503/504 phrased without that word escalated immediately with zero retries -- the opposite of the intended behavior for the textbook transient case. Fixed: added explicit 5xx markers, and switched the bare-digit status-code check (`"429" in msg`) to a word-boundary regex so it can't false-positive on a request id or token count that happens to contain those digits.
  - **`MALFORMED_OUTPUT` from the generate stage got zero retries** (`retry_policy.py`): `classify_api_error` already labels some provider-raised `ValueError`s `MALFORMED_OUTPUT`, but the generate-stage `except` block only ever retried `TRANSIENT`. Fixed: it now retries `MALFORMED_OUTPUT` there too, using the same 1-retry budget and corrective instruction as a parse failure.
  - **Groq SDK's own hidden retry/timeout defaults weren't accounted for**: Groq's client defaults to `max_retries=2` and its own 60s timeout, meaning one "attempt" from `run_llm_tier`'s point of view could cost up to 3 real HTTP requests, racing against the 62s wrapper mid-SDK-retry. Fixed: `groq.Groq(max_retries=0, timeout=...)` -- the tier's own retry policy is now the only one in play.
  - **Tier failure detail was collected then discarded**: `TierResult.error` / `.attempts_log` were populated but never made it past `_run_llm_chain` into the memo/CLI output, so a genuine bug in a provider module was indistinguishable from a real provider outage in the output. Fixed: both are now included in `tier_attempts`.
  - **`groq` missing from `requirements.txt`**: installed in `.venv` but never pinned, so a fresh `pip install -r requirements.txt` would fail on `import groq`. Fixed: added `groq==1.6.0`.
  - **Negation-window constant didn't match its own implementation** (`rule_based_fallback.py`): `NEGATION_WINDOW = 8` (words) but `_is_negated` only sliced the preceding 40 characters (~6 words) before counting -- the stated window was silently unreachable. Still correct for the case it was built for (worked by luck), but fixed the slice to actually honor the stated word count.
  - **Rule-based tier's quotes skew reference-comparison verdicts**: `rule_based_fallback` extracts fixed +-250-char context windows, not tight phrases, so they score systematically lower against `MATCH_THRESHOLD` (calibrated on LLM-length quotes) -- "deviates from standard" means something different on this tier. Not a code bug (the threshold is already documented provisional, tuned in Phase 4), so left the threshold alone; added a caveat line to the memo when `fallback_tier == "rule_based"` instead of letting the verdict be read as equivalent across tiers.
  - Reviewed and left alone: `NEGATION_GUARDED_CATEGORIES` scoping (confirmed correct against Anti-Assignment's "not assignable"), retry-loop termination bound, backoff timing, the daily-vs-per-minute 429 heuristic, and `llm_claimed_present_but_ungrounded` (confirmed dead code under the current all-or-nothing tier-level grounding-failure design -- documented as such rather than redesigned to per-category escalation, which would be a real behavior change beyond a bug fix; noted here as a candidate if that design is revisited).
- What I'd change if I did it again: run this kind of adversarial-shape review (malformed LLM output, missing infra, resource lifecycle) *during* initial implementation, not after -- the fault-injection tests I wrote myself all tested failure modes I already knew the code handled, which is a natural blind spot for self-review.
